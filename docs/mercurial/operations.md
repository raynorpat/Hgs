# Operating and recovering the service

Only `/hg/<owner>/<repo>` is public HTTPS transport. `<repository-root>/<immutable numeric ID>/.hg` is internal storage, never a web route, working checkout or public static directory. Rename and transfer retain the immutable ID. SSH uses `ssh://hg@host:2222/owner/repo`; HTTPS uses `https://host/hg/owner/repo`. Use native `hg clone`, `hg push`, and `hg pull`. HTTPS accepts a local/provider password or an access token as username with a nonempty placeholder password (`token:x`); protect both with TLS.

## Authorization, limits and shutdown

Writers are checked at `pretxnopen` and `prepushkey`. Transactions that are already open when authority changes may complete; there is no writer transaction-close veto. New transactions/key mutations after revocation are denied. Readers have static deny hooks on all veto-capable hooks. Live session cancellation is best-effort and guarantees neither completion nor rollback/store integrity. Never automatically replay an ambiguous write: inspect repository state and client status first. See [transport evidence](transport-evidence.md) and [credential freshness](operator-notes.md), including LDAP/SMTP provider-only resets being checked at next HTTPS authentication without continuous upstream revalidation.

`MAX_PROCESSES` bounds Mercurial children; `SESSION_TIMEOUT` bounds transfers in minutes (default 30); runner idle/output limits also apply. Browser reads share bounded process capacity. Process-per-request operation has measurable overhead; Task14's 200-file pages are not a scale benchmark. A transformed 98-changeset Mozilla subset has local measurements; full-source integrity verification and full-scale hosting acceptance remain failed or unverified. See [benchmark scope and receipts](mozilla-central-benchmark.md). Client disconnect/timeout may cancel work; inspect the native repository after ambiguous completion. Do not manually kill arbitrary host processes.

Stop public admissions at the listener/proxy and stop all writers before backups. Let active HTTP/SSH/browser work finish; request graceful process shutdown (SIGTERM/interrupt as supported by your process supervisor), and wait for the application and its owned Mercurial/hook children to exit. The service stops admissions, drains, and cancels on its bounded shutdown deadline. Confirm successful clean exit and no remaining writers. A forced kill alone is not a clean-backup guarantee: recover/check the database and stores while isolated before treating a snapshot as consistent. Windows package evidence uses a test-owned hidden console and a targeted CTRL_BREAK to exercise normal shutdown; production Windows service-manager integration remains unverified. Keep a bounded forced-stop fallback for failed shutdown, then investigate before backup.

## Cold backup and tested SQLite restore

The validated procedure is a **cold, consistent snapshot**, not the retired `dump` command (which is not registered). Use the same executable/assets and Mercurial runtime for initial recovery.

1. Stop admissions, drain every writer and cleanly stop the application; stop any other application/model process using this database. Confirm no workers remain and close database handles.
2. Copy the actual SQLite database **and any remaining `-wal`, `-shm`, `-journal` sidecars** after clean shutdown. Capture the entire ID-keyed repository root, the complete private `[mercurial] REVIEW_ARTIFACT_ROOT` (default `data/pull-comparisons`), actual config/secrets, persistent SSH host key, TLS material, issue attachment files, uploaded avatars, Gravatar cache if retained, and file-backed sessions if used, all at that same stopped point. Include every comparison snapshot and its `comparison-owner.json` marker, the prepared-operation namespace and `merge-owner.json` markers, and external attachment files referenced by DB paths. Review artifacts are persistent history, not a rebuildable cache, and are deliberately separate from the published repository stores. Restrict access to the backup: it contains credentials/private keys. Record source paths and repository tips, account membership/access, issue content and SSH fingerprint. Copying the zip alone does not back up user data.
3. Restore the snapshot to a new isolated directory with private access under the intended service identity. Retain executable-relative persistent paths. Change only deployment paths/listeners in a *copy* of the backed-up config: absolute database/repository/key/TLS/custom/session/log/managed-hgrc paths must point to the restored state. Set `REVIEW_ARTIFACT_ROOT` to the restored private artifact root; never place it under public/static files or published stores. Attachment records and durable prepared-operation expectations contain absolute paths: preserve their original locations for recovery, or perform a separately planned, validated path migration before starting. Changing only the configuration does not remap those durable operation paths. Do not overwrite a live installation. Regenerate only derived managed hgrc; do not regenerate the host key or application secret.
4. Enforce owner-only host-key permissions before exposure. On Unix use an owner-readable/writable key and private parent; on Windows apply a protected owner-only DACL for the service identity. Startup rechecks/reapplies key permissions; verify the resulting ACL and fingerprint. Protect database/config/TLS backups similarly. Do not grant broad access just to make startup pass.
5. Start isolated with the explicit restored config. Compare native `hg log -r tip -T '{node}'` and `hg verify` for every store; confirm issue/comment content, membership and reader/writer/stranger permissions. Verify the SSH public fingerprint equals the original, then use both HTTPS and SSH native clone/push/pull and attempt a denied reader write. Check uploads/avatars and any persistent-session files. Open an accepted historical PR comparison whose source was deleted and confirm its retained files, review events and access policy. For a backed-up durable merge operation, verify its exact operation ID, pins, result and ownership markers; observe normal reconciliation of that same operation, without creating a replacement merge. Missing or mismatched artifacts require operator repair from the same snapshot; they cannot safely be reconstructed or blindly replayed. Only reopen admissions after these checks.

Task15 exercises this on Windows/SQLite using actual extracted package processes and fresh restore paths; exact evidence and its limits are in [compatibility](compatibility.md). Fixture persistent-file canaries establish copy/retention, not a browser upload/session-authentication acceptance test. The final review regression `TestColdRestorePullArtifacts` additionally copies a stopped SQLite/repository/artifact/key snapshot, restores it at the same isolated absolute paths, serves accepted historical file bytes after source deletion, and reconciles a prepared operation with its original result and identity. It does not certify arbitrary path remapping or power-loss recovery. No MySQL/PostgreSQL consistent-snapshot procedure or external database restore was executed; use database-specific snapshot coordination and test recovery separately. A live filesystem copy and a matching-looking repository directory are not recovery proof.

## Diagnostics and unsupported surfaces

Missing or non-absolute `EXECUTABLE`, Mercurial <5.0, invalid version/capability output, an unwritable managed-config/key path, mismatched templates, or unsupported Windows path encoding fail startup with diagnostics. Record the native error, configured executable/runtime/version, path and active code page. Install a complete Mercurial runtime separately; copying `hg.exe` alone from a Python installation is insufficient. Do not repair startup by changing operator-wide hgrc/Git config or enabling ambient extensions. Managed config disables extension-specific protocols and obsolescence exchange; legacy bundle1/pushkey stays available.

Local Mercurial forks and pull requests support immutable comparisons, reviews and guarded merge publication. Forks retain native history; unmerged review commits stay outside target-cloneable storage. External-server forks, Git hosting, mirrors/imports, releases, archives, web editing, editable hooks, push webhooks/feeds, automatic issue closing, subrepository traversal and extension-specific protocols remain unsupported. See [removed features](removed-features.md). Historical Docker, assembler, init/systemd, shell build/start/autoboot/supervisord, buildpack and distro recipes are retired; no verified container/service package is supplied. License and translator attribution remain in the native package.

## Maintenance and standalone status pages

To enter maintenance, stop the current application using the normal graceful-stop procedure above, set `[server] MAINTENANCE_MODE = true` in the selected custom configuration, and restart. To resume, stop normally, set it to false, and restart. This setting is read once at process startup; editing the file does not change a running server. There is no Admin toggle, automatic drain, retry, or refresh. Starting a separate maintenance process does not stop an older process or prove that active writes have drained; verify the old process and its owned workers have stopped before maintenance work.

`MAINTENANCE_MESSAGE` is optional escaped plain text, at most 300 Unicode characters with no control characters. `MAINTENANCE_RETRY_AFTER` defaults to 300 seconds and must be 60–86400. It supplies HTTP Retry-After, not an estimate of when maintenance will finish. Invalid values fail startup before database, mail, sessions, repository storage, hosting or SSH initialization, including when maintenance is disabled.

Maintenance startup loads configuration and preloads only local status templates, locale text and the status assets. It does not initialize application services, repository/contribution workers or the embedded SSH listener. Ordinary requests, API requests and Mercurial HTTPS requests receive 503/no-store; API and Mercurial clients receive plain text. Only GET/HEAD of the exact status CSS, beaker, three approved illustrations and `/status/help` are available under the configured application sub-URL. The Check again link performs a new GET at the application root; it never resubmits a form or transport write.

The internal Mercurial hook remains a configuration-free callback to the parent process's transaction authorization service. It is not a public transport command, and cannot acquire a write grant from a maintenance-only process. Do not change its authorization or advisory publication-notification behavior to implement maintenance. Existing already-open transactions belong to the original process and its normal shutdown policy.

404/500/503 responses use standalone pages with no account sidebar or database footer. Early panics produce safe 500 text; failures after headers or streaming data are committed terminate the incomplete response. Error details remain in server logs, not public pages. Missing or damaged status templates/illustrations produce a plain-text response with the original status. Keep the packaged templates, `public/css/app.css`, `public/css/status.css`, beaker and approved status PNGs with the executable's configured static assets. Restart after replacing these resources because the standalone renderer preloads them.
